# दायरा और श्रेणीकरण

## संग्रह की परिभाषा

संग्रह में स्वतंत्र रिपॉज़िटरी शामिल की जाती हैं जिनका मुख्य लक्ष्य Agent लॉन्ग-टर्म मेमोरी है: सेशन-से-बाहर की जानकारी कैप्चर करना, व्यवस्थित करना, क्वेरी करना, अद्यतन करना या inject करना; साथ ही वे फ़ाइल मेमोरी, ग्राफ़ इंजन, कोडिंग-असिस्टेंट प्लगइन, अनुभव Skill और इवैल्युएशन टूल जो सीधे इन प्रवाहों की सेवा करते हैं।

साधारण vector डेटाबेस, ग्राफ़ डेटाबेस, Agent फ़्रेमवर्क का कोई built-in फ़ील्ड, और केवल chat-window cache रखने वाले प्रोजेक्ट स्वतंत्र मेमोरी सिस्टम नहीं माने जाते। पूर्ण Agent प्लेटफ़ॉर्म, रिट्रीवल टूल और context-कलेक्शन ऐप "संलग्न" श्रेणी में तभी आते हैं जब वे प्रायः मेमोरी समाधान में इस्तेमाल हों या सीमा तय करने में स्पष्ट मूल्य रखें।

## आठ मुख्य श्रेणियाँ

| श्रेणी | मुख्य निर्णय-प्रश्न |
| --- | --- |
| मेमोरी इंजन और सर्विसेज़ | क्या पूर्ण ingest, स्टोरेज, रिट्रीवल, अद्यतन या reflection API मिलती है? |
| फ़ाइल-आधारित ट्रुथ सोर्स और समीक्षायोग्य मेमोरी | क्या साधारण फ़ाइलें संपादन-योग्य, स्थानांतरण-योग्य तथ्य-स्रोत हैं, और इंडेक्स दोबारा बनाया जा सकता है? |
| ग्राफ़, एंटिटी और टेम्पोरल मेमोरी | क्या मुख्य मॉडलिंग एंटिटीज़, संबंध, टाइम वैलिडिटी, derivation या मल्टी-हॉप क्वेरी की है? |
| कोडिंग Agent और MCP मेमोरी | क्या यह मुख्यतः Claude Code, Codex, OpenCode जैसे होस्ट्स और प्रोजेक्ट इंजीनियरिंग मेमोरी की सेवा करती है? |
| अनुभव, स्किल और प्रोसीजरल मेमोरी | क्या execution traces को पुनःप्रयोज्य संचालन, रणनीति, Skill या workflow में बदला जाता है? |
| रिसर्च इम्प्लीमेंटेशन और इवैल्युएशन | क्या यह मुख्यतः पेपर तंत्र, डेटासेट, सुरक्षा/forgetting मुद्दे या benchmark दोबारा प्रस्तुत करती है? |
| संलग्न प्लेटफ़ॉर्म, स्पेसिफ़िकेशन और इंडेक्स | क्या यह पूर्ण Agent प्लेटफ़ॉर्म, रिट्रीवल घटक, स्पेसिफ़िकेशन या कवरेज इंडेक्स है? |
| ऐतिहासिक, आर्काइव्ड और प्रतिबंधित लाइसेंस | क्या यह archive/deprecated हो चुका है, या इसका लाइसेंस सामान्य OSI ओपन-सोर्स नहीं? |

हर रिपॉज़िटरी केवल एक मुख्य श्रेणी में रखी जाती है। समान नाम वाली परियोजनाओं के साथ owner अनिवार्य है; `MemOS`, `MemoryOS`, `EverOS`, और कई `Engram`, `MemForest`, `agent-memory` भिन्न-भिन्न इकाइयाँ हैं।

## निर्णय की सीमाएँ

- सहेज लिए जाना इस बात की गारंटी नहीं कि आगे recall सही होगा, और recall सफल होना इस बात की गारंटी नहीं कि Agent उसे सही इस्तेमाल करेगा।
- Markdown का समीक्षा-योग्य होना summary-विसर्जन को खत्म नहीं करता; ग्राफ़ और संबंध तथ्यों की शुद्धता की गारंटी नहीं देते।
- स्रोत रिकॉर्ड हटाने से स्वतः यह सिद्ध नहीं होता कि सारांश, निष्कर्ष, ग्राफ़ किनारे, skills, इंडेक्स और caches सब साफ़ हो गए।
- scope, bank, collection, डायरेक्टरी और workspace आपस में अदला-बदली करने योग्य tenant सुरक्षा-सीमाएँ नहीं हैं।
- self-hosted डेटा का अर्थ स्वतः यह नहीं कि embedding, एक्सट्रैक्शन, rerank और reflection मॉडल नेटवर्क से बाहर नहीं जाते।
- प्रोजेक्ट का benchmark केवल तभी तुलनीय है जब मॉडल, डेटा-स्प्लिट, बजट, judge और संस्करण एक जैसे हों।
- ओपन-सोर्स कोर, होस्टेड सर्विस, कमर्शियल संस्करण और प्लगइन अलग-अलग लाइसेंस या डेटा-पाथ इस्तेमाल कर सकते हैं।

## स्तरीय पठन

प्रोजेक्ट एंट्री "पोज़िशन, सीमा, लाइसेंस, फ़िक्स्ड-कमिट प्रमाण" देती है। मेंटेनेंस रैंकिंग केवल वर्तमान ध्यान और development गतिविधि आँकने में मदद करती है। वास्तविक चयन के लिए समान चीनी सामग्री पर कैप्चर, correction, प्रोजेक्ट-आइसोलेशन, deletion, बैकग्राउंड recovery, P50/P95 विलंब, मॉडल लागत और अंतिम task completion दर का परीक्षण करना चाहिए।
