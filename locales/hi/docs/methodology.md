# रैंकिंग पद्धति और सीमाएँ

## GitHub मेट्रिक्स

`scripts/refresh_metrics.py` GitHub GraphQL API से एक UTC क्षण में सभी canonical रिपॉज़िटरीज़ का डेटा पढ़ता है। `data/metrics.json` परमाणु रूप से तभी बदला जाता है जब सारे बैच सफल हों; आंशिक विफलता पर पुराना स्नैपशॉट बना रहता है और task fail हो जाता है।

- `stars`: संग्रहण के समय लोकप्रियता का proxy संकेतक।
- `commits_30d / commits_90d`: डिफ़ॉल्ट ब्रांच के इतिहास में तय विंडो के पूर्ण commit counts, जिनमें merge, bot और documentation commits शामिल हैं।
- `last_commit_at`: डिफ़ॉल्ट ब्रांच HEAD commit का समय।
- `pushed_at / updated_at`: audit के लिए सुरक्षित; इन्हें डिफ़ॉल्ट ब्रांच के कोड अद्यतन का समय बताकर पेश नहीं किया जाता।
- `latest_release`: सबसे नई बनाई गई release; उसके न होने को स्वतः abandonment नहीं माना जाता।
- `archived / disabled`: GitHub रिपॉज़िटरी की स्थिति।

## टियरिंग और सूत्र

पहले मेंटेनेंस स्थिति से चार टियर: पिछले 90 दिनों में कमिट; 91–365 दिन निष्क्रिय; 365 से अधिक दिन निष्क्रिय; आर्काइव्ड, disabled या ऐतिहासिक प्रोजेक्ट।

```text
P = min(1, ln(1 + stars) / ln(1 + 100000))
A = min(1, ln(1 + commits_90d) / ln(1 + 500))
R = exp(-max(0, days_since_default_branch_HEAD) / 90)
मेंटेनेंस स्कोर = 100 × (0.40 × P + 0.35 × A + 0.25 × R)
```

समान स्कोर पर पहले star से तुलना, फिर रिपॉज़िटरी नाम से stable sort। समग्र स्कोर, star, 90-दिन गतिविधि और नवीनतम कमिट — चारों व्यूज़ पहले मेंटेनेंस स्थिति से टियर होते हैं। बिना-टियर कच्चे मानों के लिए CSV इस्तेमाल करें।

## इससे क्या निष्कर्ष नहीं निकाल सकते

मेंटेनेंस स्कोर LongMemEval, LoCoMo, recall, उत्तर-शुद्धता, deletion-पूर्णता, सुरक्षा या प्रोडक्शन परिपक्वता नहीं है। monorepo और automated commits गतिविधि बढ़ा दिखाते हैं, स्थिर छोटी लाइब्रेरीज़ कम आँकी जा सकती हैं, और रिसर्च रिपॉज़िटरीज़ को लगातार उच्च-आवृत्ति commits की ज़रूरत नहीं होती।

लाइसेंस auto-identification और manual समीक्षा अलग-अलग रखे जाते हैं। `NOASSERTION` को डिफ़ॉल्ट से MIT नहीं लिखा जाता; PolyForm, BSL, non-commercial, dual license और विभाजित लाइसेंस मूल सीमाओं के साथ रखे जाते हैं। मॉडल वेट्स, डेटासेट, तृतीय-पक्ष निर्भरताएँ और होस्टेड सर्विसेज़ के लाइसेंस अलग हो सकते हैं।

## क्षमता-मूल्यांकन का सुझाव

एक ही मॉडल, token बजट और डेटासेट पर अलग-अलग मापें: लेखन-पूर्णता, समय/एंटिटी/मल्टी-हॉप recall, प्रमाण-हिट, उत्तर-शुद्धता, यूज़र-correction का प्रभाव, single-shot exception दूषण, क्रॉस-प्रोजेक्ट आइसोलेशन, deletion-के-बाद residual, प्रोसेस recovery, P50/P95 विलंब और कुल लागत। Vendor के अलग-अलग सर्वोत्तम आँकड़ों से लीडरबोर्ड न बनाएँ।
